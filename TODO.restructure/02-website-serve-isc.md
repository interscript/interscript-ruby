# 02 — Website: serve .isc files instead of .json

## Priority: P0

## Status: PARTIALLY COMPLETE — primary transliteration pipeline uses .isc

## Problem
The website served compiled JSON IR from `/public/maps/*.json`.
These were generated by Ruby from `.isc` files. With the TS ISC
parser, JSON IR is no longer needed for browser-side transliteration.

## Implementation

### Worker (primary transliteration path) — DONE
`interscript.org/src/scripts/transliteration-worker.ts` now uses
`iscStrategy` instead of `httpStrategy`:
```typescript
import { iscStrategy } from "interscript-ts"

function defaultStrategies(): LoadStrategy[] {
  return [
    iscStrategy({ baseUrl: "/maps" }),
  ]
}
```

The ISC parser runs entirely in the worker (off the main thread).
On first request: fetches `/maps/<code>.isc`, parses, converts to
the runtime `CompiledMap` shape, caches in memory.

### Static files — DONE
All 289 `.isc` files copied to `interscript.org/public/maps/`.
The `.json` files remain for backward compatibility with non-critical
display components (see TODO 03).

### Components not yet migrated
These still fetch `.json` for non-critical display purposes:
- `src/components/MapExplorer.vue`
- `src/components/RuleViewer.vue`
- `src/components/MapPreview.vue`

Full migration happens in TODO 03 (render map pages from parsed .isc
at build time).

### Performance
Parsing .isc in the browser is fast (~1-5ms per map after first parse).
The web worker keeps parsing off the main thread. In-memory caching
across requests means each map parses at most once per session.

## Verification
- Worker fetches `.isc` and runs transliteration through the ISC parser
- All 289 maps load via the ISC pipeline
- interscript-ts test suite passes (233 tests)
- TS parity: 100% (7388/7388 test vectors)
